互斥与中断

如何实现互斥？

思路：能否使当前程序状态机独占计算机系统？

中断是在单核处理器系统中造成并发的最主要原因，如果能够屏蔽所有中断，就可以很轻易的实现单个 CPU 的原子性。

[!NOTE]

不同指令系统实现原子性的指令（不响应中断）：

  • x86: cli 清除 eflags 中的 IF bit
  • RISC-V: 清除 mstatus 的 MIE bit
  • AArch64: msr daifset, #3
    • 程序死循环 = 计算机系统卡死

这些指令都是用于在不同架构的计算机中禁用中断或异常处理机制的一部分。它们的作用是在处理器状态中清除某个标志位，从而阻止外部事件（如硬件中断）打断当前正在运行的程序。

不是所有的中断都可以由外部终止响应，有不可屏蔽中断。

关中断：不是万能的

  • 操作系统可以，但普通程序不行

    • 中断保证了死循环不能把计算机 “卡死”

    • 操作系统不允许普通程序关中断

      • 但如果是操作系统代码，完全可以短暂关闭中断

  • 单处理器系统可以，多处理器系统不行

    • 每个处理器有独立的寄存器组

    • 中断是每个处理器内部状态

[!IMPORTANT]

Stop-the-world 实现互斥：对于操作系统上的应用程序，关闭中断是不能容忍的：这会使微小的 bug 或是恶意的程序破坏计算机的运行。操作系统正是因为统治了中断，才实现了对应用程序的管理。在操作系统内核的实现中，关闭中断是一个常见的操作。

使用 Load/Store 实现互斥（Peterson 算法）

Dekker’s Algorithm (1965)

绕口令：A process P can enter the critical section if the other does not want to enter, otherwise it may enter only if it is its turn.

如果其他进程不想进入临界区段，则进程 P 可以进入临界区段，否则只有轮到自己时才能进入。

Peterson’s Algorithm (1981)

还是绕口令：A process P can enter the critical section if the other does not want to enter, or it has indicated its desire to enter and has given the other process the turn.

如果另一个进程不想进入临界区段，或者该进程已表示希望进入临界区段，并让另一个进程进入临界区段，则进程 P 可以进入临界区段。

假设：

  • 任何时候可以执行一条 load/store 指令
  • 读/写本身是原子的

多处理器系统上的互斥

在多处理器上实现互斥，为什么不能向现实世界中一样，多个人上厕所等待呢？

原因在于 load/store 是两个原子性的操作，load 相当于观察，store 相当于做事。现实生活中上厕所时，虽然观察和做事是两个动作，但是每个人可以知道是否有其他人也在跟自己做同样的事情。但是在多处理器上实现互斥时，处理器之间访问临界区时并不知道其它处理器的状态，会存在两个处理器同时观察（load），且都认为自己访问临界区的条件满足，然后同时进入临界区做事（store）的情况，从而引起错误。

解决方法：不可打断的 load + 计算 + store

解决互斥问题的正确姿势是用改变硬件（增加一条原子指令），而不是深究软件算法。

在硬件原子指令基础上实现基础版本的自旋锁

自旋锁是一种用于同步多线程的机制，它允许一个线程在等待另一个线程释放资源时原地旋转（或“自旋”）而不是进入睡眠状态。

  • atomic_xchg() 函数是一个原子交换操作，将给定的值与目标变量进行交换并返回旧值。

  • lock() 函数：尝试获取锁。它在一个循环中调用 atomic_xchg() 来尝试设置 status 变量为锁定状态（标记为“×”）。如果交换操作失败（即当前 status 不是解锁状态），则执行 goto retry; 重新尝试。

  • unlock() 函数：释放锁。它简单地调用 atomic_xchg() 将 status 变量恢复到解锁状态（标记为“√”）。

Test-And-Set (TAS), Compare-And-Swap (CAS), and Compare-And-Exchange (COMPXCHG) 都是原子操作，用于实现线程间的同步。这些操作对于并发控制非常重要，特别是在多处理器或多核系统中。

Test-And-Set (TAS)

Test-And-Set 是一种基本的同步原语，用于实现互斥锁。这个操作通常由两个部分组成：

  1. 测试 - 检查锁是否已经被其他线程持有。
  2. 设置 - 如果锁未被持有，则设置锁的状态为已持有。

TAS 操作通常是这样的：

  • 如果锁当前处于未锁定状态，则将其设置为锁定状态，并返回 true。
  • 如果锁当前处于锁定状态，则不改变其状态，并返回 false。

Compare-And-Swap (CAS)

Compare-And-Swap 是一种更强大的同步原语，它可以用来实现更复杂的同步结构，比如无锁数据结构。CAS 操作包含三个参数：

  1. 内存位置 (V) - 要修改的内存地址。
  2. 期望值 (E) - V 中期望找到的值。
  3. 新值 (D) - 如果 V 包含 E，则用 D 替换 E。

CAS 操作会检查 V 当前的值是否为 E。如果是，则将 V 设置为 D 并返回 true；如果不是，则不改变 V 的值并返回 false。

Compare-And-Exchange (COMPXCHG)

Compare-And-Exchange 与 CAS 类似，但通常指代的是一种更具体的指令，特别是在某些处理器架构上。它也接受三个参数，并执行同样的比较和交换操作。尽管术语上有所不同，但在大多数情况下，COMPXCHG 和 CAS 是可以互换使用的。

使用 cmpxchg 实现自旋锁：原子的 load-store 可以帮助我们实现：

  1. 取出内存中的数值；
  2. 写入一个数值，并且指令的执行在多处理器系统上依旧带有 “stop-the-world” 的效果。

因此，无论有多少线程同时执行 lock()，仅有一个能获得 UNLOCKED 的数值，从而实现互斥。

终于，我们借助计算机硬件提供的短时原子性实现了多处理器间的互斥。

自旋锁-API

  • lock_t 表示锁的数据结构
  • lock 和 unlcok 应该明确指定要对哪个锁进行操作（操作系统中可以有很多锁来控制对不同临界区资源的访问）
  • 通过设计实现线程安全，以及避免死锁

lock/unlock 并没有 “stop the world”：

  • 只是同一把锁保护的代码被串行化了

  • 只有正确使用锁，才能实现 “stop the world” 的效果。反例：

操作系统内核中的自旋锁

在中断处理程序中调用锁

操作系统就是 C 程序，这个 C 程序掌管了整个计算机系统的硬件，每一个线程上运行的都是操作系统的代码。

多个 CPU，每个 CPU 都有各自独立的寄存器组和 SP，有独立的 Stack，但是有一个共享内存。

[!IMPORTANT]

计算机系统内核中实现自旋锁需要考虑中断。考虑一种场景——在中断处理程序中调用锁：

某个 CPU 执行 lock，然后进入临界区工作，在工作期间，操作系统响应了中断，然后中断处理程序中也尝试进入临界区，它会尝试交互获得锁的使用权，但因为进入中断处理程序之前没有 unlock，所以中断处理程序中会不断自旋，导致中断处理程序无法返回，结果就是系统崩溃。

解决方法：在lock之前关闭中断

真正正确性的准则应该是：上锁/解锁前后中断状态不变

问题：需要在 unlock 之后重新打开中断吗？

答案是否定的。设想一种场景，在一个中断处理程序中，要对临界区资源进行访问，lock之前关闭了中断，unlock之后打开中断，但是在中断处理程序中是不能随意的打开中断的。

另一个场景——锁的嵌套：假设有lock_A 和 lock_B两把锁，CPU执行的顺序是： lock_A——lock_B——unlock_B——unlock_A，我们希望的是在lock_A前和unlock_A后的中断状态不改变，那么unlock_B就不能随意打开中断。

应用程序中的互斥

为了避免多个线程争抢锁时陷入无意义的自旋状态而造成资源的浪费，可以通过系统调用在内核态实现 lock和unlock，如果获取锁失败，就进入睡眠状态，同时切换到其它线程执行，而不必一直自旋。等待该锁被释放，内核再将该线程唤醒。

pthread 互斥锁（pthread_mutex_t）与自旋锁不同，设计上就避免了在多个线程争抢锁时一直自旋浪费资源。具体来说，当一个线程尝试获取已被其他线程持有的互斥锁时，pthread 互斥锁会使该线程进入阻塞状态，而不是不断自旋等待。这种机制通过操作系统的调度器来实现，避免了 CPU 资源的浪费。下面是具体原理：

  • 阻塞等待：当一个线程试图获取一个已被其他线程持有的互斥锁时，pthread 会使该线程进入阻塞状态，而不是让线程不断循环检查锁的状态。
  • 唤醒机制：当持有锁的线程释放锁时，会唤醒一个或多个阻塞在该锁上的线程，使它们重新竞争锁。
  • 调度器管理：通过操作系统的调度器管理线程的状态，使得 CPU 资源能够被其他可运行的线程使用，而不是被自旋锁浪费。

Take-away Messages

“互斥” 看起来简单，用自旋就能实现，但如果在实际的场景 (例如可被中断的操作系统内核、不希望浪费 CPU 资源的应用程序等)，实际的互斥实现就不再简单。我们在 xv6 的自旋锁实现中，发现了许多 “防御性编程” 的例子，先假设程序员可能会犯一切可能的错误——然后不断加以检查。而 “正确性完全由开发者负责” 的时代将要过去，我们将会在未来越来越多地看到编程语言中的机制，帮助我们写出正确的代码。

并发调试理论与实践

[!IMPORTANT]

调试理论给了大家在遇到 “任何问题” 时候 self-check 的列表：

  1. 是怎样的程序 (状态机) 在运行？
  2. 我们遇到了怎样的 failure？
  3. 我们能从状态机的运行中从易到难得到什么信息？
  4. 如何二分检查这些信息和 error 之间的关联？

Perf 是 Linux 下的一个性能分析工具，它可以用来收集和分析 CPU 的性能事件。

Strace 可以监控一个进程的系统调用和信号处理，这对于诊断、调试和记录程序如何交互与操作系统非常有用。

小范围假设（Small Scope Hypothesis）是由丹尼尔·杰克逊（Daniel Jackson）提出的，主要用于软件验证和模型检查领域。这个假设的核心思想是：

如果一个系统在小范围（即有限的规模或配置）内对于某个特定属性没有出现反例（即错误或漏洞），那么在更大范围内出现反例的可能性也很低。

简单来说，小范围内没有问题，大范围内通常也不会有问题。

这个假设背后的逻辑是，大多数错误或漏洞在小范围内就能被发现，因为它们往往是由基本的逻辑错误或设计缺陷引起的，这些错误在系统规模较小时就会显现出来。因此，通过在小范围内进行详尽的测试或验证，可以有效地发现大多数潜在的问题，而不需要在更大范围内进行同样详细的检查。
