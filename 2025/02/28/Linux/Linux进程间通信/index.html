进程间通信

进程间通信（interprocess communication，简称 IPC）指两个进程之间的通信。不同的进程都在各自的地址空间中、相互独立、隔离，所以它们处在不同的地址空间中，因此相互通信比较难。

每个进程的用户空间是独立的，但是内核空间却是公用的。所以，IPC 必须由内核来提供服务，Linux 内核提供了多种进程间通信的机制。

管道

管道（Pipe）是 UNIX 系统上最古老、最简单的 IPC 方法。

管道实现的核心思想是利用内核提供的一小块内存（环形缓冲区）来临时存储数据，从而使得两个进程能够通过这个共享的缓冲区进行数据交换。

  • 缓冲区的数据以环形队列的形式存储，大小默认为 4k（依赖具体版本）。
  • 管道分为两部分：读端和写端（队列的两端），数据从写端进入管道，从读端流出管道。
  • 管道中的数据只能读一次，读数据相当于出队列。
  • 管道是单工的：数据只能单向流动。
  • 对管道的读、写默认是阻塞的：如果缓冲区满，写入进程会被阻塞；如果缓冲区空，读取进程会被阻塞。

缓冲区存储在内核中，不能直接对其进行操作，那么该怎么读写管道呢？

管道操作本质上是一种特殊的文件 I/O 操作，内核将管道抽象为两个文件描述符，分别对应读端和写端。

匿名管道

匿名管道(Anonymous Pipe)主要用于有亲缘关系的进程（如父子进程、兄弟进程）之间的单向数据流动。

匿名管道就是 Linux 中的 |，比如 ps auxf | grep mysql。这个竖线就是匿名管道，它的作用就是将前一个命令的输出作为后一个命令的输入。

匿名管道的特点是：单向通信、仅限于亲缘进程、随进程结束而销毁、不占用磁盘空间。

pipe() 通常配合 fork() 使用，父子进程通过继承的文件描述符通信。

父进程会首先创建一个管道，得到读端 fd[0] 和写端 fd[1] 两个文件描述符。父进程 fork() 创建子进程后，子进程也会继承这两个文件描述符。

如果数据是从父进程流向子进程，那么父进程就会关闭读端，只保留写端，而子进程只需要反着来，关闭写端只保留读端。也就是说，两个通信的进程分别得到同一个管道的入口和出口，就可以进行数据传输了。

[!info] Shell 中的匿名管道是怎么实现的？
当你在 Shell 中使用 cmd1 | cmd2 时：

  1. Shell 调用 pipe() 创建管道（fd[0], fd[1]）。
  2. fork() 两次，创建 cmd1 和 cmd2 进程：
    • cmd1（写端）：
      • 关闭 fd[0]（不需要读）。
      • 把 STDOUT (1) 重定向到 fd[1]：dup2(fd[1], 1)。
    • cmd2（读端）：
      • 关闭 fd[1]（不需要写）。
      • 把 STDIN (0) 重定向到 fd[0]：dup2(fd[0], 0)。
  3. 两个进程独立运行，数据通过内核缓冲区流动。

有名管道 FIFO

与匿名管道相对的是有名管道（Naemed Pipe），在 Linux 中称为 FIFO，即 First In First Out，先进先出队列。

FIFO，即 First In First Out，先进先出队列。FIFO 是 Linux 中的一种特殊文件类型，而之所以称之为有名是因为管道存储在于文件系统中，可以通过路径名访问，对应的文件类型为 p。

有名管道也是利用内核在内存中提供的环形缓冲区，它的文件大小永远是0。任何进程只要知道路径，都能打开并到操作管道的文件描述符来通信。

有名管道与普通管道（匿名管道）的主要区别在于：

  • 普通管道是匿名且临时的，只能在有亲缘关系的进程间使用；
  • FIFO 是有名称的持久化管道，可以在任意进程间通信。

内存映射

内存映射（Memory Mapping）是一种将文件或设备的内容映射到进程地址空间的技术。

通过 mmap() 系统调用，可以将文件或匿名内存映射到进程的虚拟地址空间中，多个进程可以通过映射同一块内存区域来共享数据。

  • 文件映射 ：将文件内容映射到内存，多个进程可以通过映射同一文件来共享数据。
  • 匿名映射 ：不依赖于文件，直接创建一块共享内存区域，多个进程通过父子关系共享这块内存。

以文件映射来说，由于每个进程的地址空间是独立的，各个进程之间不能直接访问对方的内存映射区，需要通信的进程需要将各自的内存映射区和同一个磁盘文件进行映射，以此来进行数据的交互。

当进程 A 中的内存映射区数据被修改，数据会自动同步到磁盘文件，进程 B 的内存映射区也会和磁盘文件进行实时同步，从而完成数据共享。

这种通过文件映射来实现进程间通信的方法适用于任何进程。

mmap() 系统调用通过将文件的一部分或全部直接映射到进程的虚拟内存空间中，使得应用程序可以通过指针操作来访问文件内容，而不需要使用传统的 read/write 系统调用。

参数说明：

  • addr：期望映射的内存起始地址，通常设为 NULL，由内核自动选择合适地址。
  • length：映射区域的大小（字节）。实际会按页大小（4kb = 4096byte）向上取整。
  • prot：设置内存页的访问权限。以下标志可以通过按位或 | 进行组合，但权限不能超过文件打开时的模式：
    • PROT_READ：页内容可读。
    • PROT_WRITE：页内容可写。
    • PROT_EXEC：页内容可执行（如代码段）。
    • PROT_NONE：页不可访问（用于特殊用途）。
  • flags：控制映射行为的标志。以下标志可以通过按位或 | 进行组合：
    • MAP_SHARED：修改会同步到文件，允许多进程共享（进程间通信用）。
    • MAP_PRIVATE：修改仅对本进程有效（写时复制，不改变原文件）。
    • MAP_ANONYMOUS / MAP_ANON：匿名映射（不关联文件，用于分配内存）。
    • MAP_FIXED：强制使用 addr 指定的地址（需谨慎使用），如果不允许，将返回错误。
    • MAP_LOCKED：锁定内存防止被换出（需特权）。
  • fd：被映射文件的文件描述符。如果是匿名映射（需配合 MAP_ANONYMOUS 使用），传入无效的 fd 即可，比如 -1 。
  • offset：文件映射的起始偏移量，映射开始的位置。这个数必须为页大小（4k）的整数倍。如果不偏移或者是匿名映射，传入 0 即可。

返回值：

  • 成功：返回映射区域的起始地址（void* 类型）。
  • 失败：返回 MAP_FAILED（即 (void *) -1），并通过 errno 设置错误码。

共享内存

共享内存（Shared Memory）是最高效的进程间通信方式。不同于内存映射区，共享内存不属于任何进程。进程通过 Linux 提供的系统调用就可以得到这块共享内存。使用之前需要让进程和共享内存进行关联，得到起始地址就可以进行读写操作了。

共享内存的零拷贝：共享内存不需要内核来中转数据，内核通过修改进程的页表，将同一块物理内存映射到多个进程的虚拟地址空间。所以进程可以直接操作内存，相比于管道、消息队列等，减少了两次数据拷贝（用户态↔内核态↔用户态），实现了零拷贝，这也是其高效的原因。

共享内存的同步问题：需要注意的是，共享内存本身不提供同步机制。当多进程并发访问时，可能会导致数据竞争，因此需要配合信号量等外部同步工具使用。

Linux 提供了一系列系统调用来操作共享内存：

  1. shmget() ：创建或获取共享内存段。
  2. shmat() ：将共享内存段附加到进程的地址空间。
  3. shmdt() ：将共享内存段从进程的地址空间分离。
  4. shmctl() ：控制共享内存段（例如删除共享内存）。

上述的 shmget、shmat、shmdt 和 shmctl 等都是 System V 共享内存 API。它出现较早，属于 System V IPC 机制的一部分。System V IPC 包括消息队列、信号量和共享内存，这些机制在早期的 UNIX 系统中被广泛使用。它们依赖于内核中的 IPC 对象（如共享内存段），这些对象通过键值（key）进行标识，而不是文件系统路径。

而POSIX 共享内存 API属于较新的标准，设计更加现代化。它使用文件系统路径来命名共享内存对象，与文件 I/O 操作紧密结合。

  1. shm_open() ：创建或打开共享内存对象。
  2. mmap()：将共享内存对象映射到进程的地址空间。
  3. munmap()：解除映射。
  4. shm_unlink() 删除共享内存对象。
创建/获取共享内存 shmget()

shmget() 用于获取一个已经存在的共享内存段，或者创建一个新的共享内存段。

参数说明：

  • key：共享内存的逻辑标识符。类型 key_t 是个整型数，通过这个 key 就可以创建或者打开一块共享内存。传参时，可以使用 IPC_PRIVATE 自动分配一个新的 key，也可以通过 ftok() 函数生成一个唯一的 key。
  • size : 指定共享内存段的大小（以字节为单位），必须是页大小的整数倍（4KB 或更大）。
  • shmflg：标志位，指定共享内存段的权限和行为。
    • IPC_CREAT：如果共享内存段不存在，则创建它。需要指定对共享内存的操作权限，比如：IPC_CREAT | 0664；
    • IPC_EXCL：如果共享内存不存在，则创建它，否则报错。必须和 IPC_CREAT 一起使用，用于确保共享内存段是全新创建的。

返回值：

  • 成功时返回共享内存段的标识符（shmid），该标识符用于后续操作；
  • 失败时返回 -1，并设置 errno。

[!NOTE] key 和 shmid 都是标识符，二者有什么区别？

  • key：全局唯一标识符，用于跨进程定位共享内存（类似文件名）。key 是全局的。

  • shmid：当前进程内使用的内核对象句柄，用于实际操作共享内存（类似文件描述符）。shmid 是局部的。

示例一：IPC_CREAT 和 IPC_EXCL 的区别

  • 如果 key 对应的共享内存段不存在，则创建一个新的共享内存段。
  • 如果 key 对应的共享内存段已经存在，则直接返回其标识符。
  • 如果 key 对应的共享内存段已经存在，则调用失败。
  • 如果 key 对应的共享内存段不存在，则创建一个新的共享内存段。

  • 使用 IPC_PRIVATE 时，系统会确保创建的共享内存段是唯一的，不需要显式指示 key。

shmdat() 用于断开当前进程与共享内存的关联，进程不再能访问该内存，但共享内存仍然存在，其他进程仍可使用。

控制（删除、获取信息）共享内存 shmctl()

shmctl() 函数是一个多功能函数，可以设置、获取共享内存的状态，也可以将共享内存标记为删除状态。

当共享内存被标记为删除状态之后，并不会马上被删除，直到所有的进程全部和共享内存解除关联，共享内存才会被删除。

函数原型：

  • shmid：shmget() 返回的共享内存标识符
  • cmd：控制命令。
    • IPC_STAT: 获取共享内存信息（存储到 buf）；
    • IPC_SET: 设置共享内存的状态；
    • IPC_RMID: 删除共享内存段（所有进程 shmdt() 后才会真正释放）。
  • buf：存储共享内存信息的结构体（struct shmid_ds）。获取状态信息时作为传出参，设置状态信息时作为传入参，删除共享内存时可设为 NULL。

    • O_CREAT: 如果共享内存对象不存在，则创建它。
    • O_EXCL: 与 O_CREAT 一起使用，如果共享内存对象已经存在，则返回错误。
    • O_TRUNC: 如果共享内存对象已经存在，则将其截断为零长度。
  • mode : 如果使用了 O_CREAT 标志，则需要指定权限模式（类似于文件权限），例如 0666 表示所有用户可读写。
    返回值：
  • 成功：返回文件描述符（fd），用于后续 mmap 映射。
  • 失败：返回 -1，并设置 errno。

注意，shm_open() 返回的是一个文件描述符 fd，与文件系统保持一致。

  • name : 要删除的共享内存对象的名字，必须与 shm_open() 中使用的名称一致。

典型使用流程：

  1. 使用 shm_open() 创建或打开共享内存对象。
  2. 使用 ftruncate() 设置共享内存的大小。
  3. 使用 mmap() 将共享内存映射到进程的地址空间。
  4. 进行数据读写操作。
  5. 使用 munmap() 解除映射。
  6. 使用 close() 关闭文件描述符。
  7. 使用 shm_unlink() 删除共享内存对象（如果不再需要）。

消息队列

消息队列（Message Queue）允许进程之间通过发送和接收消息来进行通信。

消息队列是保存在内核中的消息链表，在发送数据时，会分成一个一个独立的数据单元，也就是消息体（数据块）。

消息体是用户自定义的数据类型，消息的发送方和接收方要约定好消息体的数据类型，所以每个消息体都是固定大小的存储块，不像管道是无格式的字节流数据。如果进程从消息队列中读取了消息体，内核就会把这个消息体删除。

消息队列的特性：

特性 说明
异步通信 发送者和接收者无需同时运行，消息会持久化在队列中直到被读取。
结构化数据 消息可以包含类型和正文，支持自定义数据结构。
解耦 生产者和消费者独立运行，通过队列中介通信。
多对多通信 多个进程可以向同一队列发送或接收消息。
内核持久化 消息队列由内核维护，即使进程退出，消息仍保留（除非显式删除）。

消息队列的不足之处，一是通信不及时，二是数据有大小限制。

和共享内存一样，Linux 为消息队列提供了 System V 和 POSIX 两种实现方式。我们这里只介绍 POSIX 相关的 API。

信号

信号是事件发生时对进程的通知机制。信号有时也称之为软件中断，因为它和硬件中断一样，打断了程序执行的正常流程。

信号是进程间通信机制中唯一的异步通信机制。

大多数情况下，我们无法预测信号到达的准确时间。进程可以向自己发送信号，但更多的信号都是源于内核。引起内核向进程发送信号的各类事件包括：

  • 硬件发生异常。硬件异常的例子包括执行一条异常的机器指令，比如除以 0、越界访问等；
  • 用户键入了能够产生信号的终端特殊字符。其中包括中断字符（通常是 Ctrl-C)、暂停字符（通常是 Ctrl-Z）。
  • 发生了软件事件。比如调整了终端窗口大小，定时器到期等等。

每个信号都有唯一的一个整数编号，从 1 开始。signal.h 中对信号的名称（ SIGXXXX）和这些整数做了定义。

信号的分类

通过 kill -l 命令可以察看系统定义的信号列表：

信号分为两大类：

  • 第一组用于内核向进程通知事件，即标准信号。Linux 中标准信号的编号范围为 1～31。
  • 一组信号由实时信号构成，编号范围为 34~64。

在 Linux 系统下，标准信号都是不可靠信号，也就是说信号可能会丢失。这些标准信号是传统的 UNIX 信号，定义在 POSIX 标准中，每个标准信号有固定的用途。

而实时信号专为实时应用设计，支持可靠传递和优先级，支持排队、支持携带额外数据，信号的用途由用户自定义。

信号的状态

信号的生命周期包含三种关键状态：

  1. 产生（Generation）：信号由某个事件触发而生成。触发源可能是：内核、其它进程、终端、硬件异常等。
  2. 未决（Pending）：信号已经生成但还没有被进程处理。可能的原因包括：进程阻塞了该信号或者内核尚未调度到目标进程。
  3. 递达（Delivery）：信号被进程接收并处理。处理的方式包括：
    • 默认行为；
    • 自定义信号处理函数（通过 signal() 或 sigaction() 注册）；
    • 忽略信号。

abort()

abort() 是 C 标准库中用于异常终止程序的函数，它会引发一个不可忽略的中断信号 SIGABRT 导致程序终止。

abort() 常用于错误处理、辅助调试、安全终止等场景下。使用时要注意：

  1. 不可恢复：abort() 总会终止程序，不管有没有捕获 SIGABRT 信号；
  2. 资源清理：不会调用 atexit() 注册的函数
  3. 文件缓冲：不会刷新标准 I/O 缓冲区（不同于 exit）
  4. 多线程：在多线程程序中，abort() 会终止整个进程
  5. 信号屏蔽：会解除对 SIGABRT 的阻塞.
定时器

定时器（Timer）用于在特定时间或间隔后执行操作。定时器通常与信号（Signal）结合使用，当定时器到期时，系统会向进程发送一个信号，从而触发相应的处理逻辑。

Linux 系统定时器可以通过 alram() 函数或 setitimer() 函数设置。

alram()

使用 alarm() 函数可以设置一个定时器（闹钟），当定时器定时时间到时，内核会向进程发送 SIGALRM 信号，这个信号默认的处理动作是中断当前进程。每个进程只能设置一个 alarm 闹钟，如果调用新的 alarm()，会覆盖之前的定时器。

函数原型如下所示：

  • seconds：设置定时时间，以秒为单位；如果参数 seconds 等于 0，则表示取消之前设置的 alarm 闹钟。
  • 返回值：如果在调用 alarm() 时，之前已经为该进程设置了 alarm 闹钟还没有超时，则该闹钟的剩余值作为本次 alarm() 函数调用的返回值，之前设置的闹钟则被新的替代；否则返回 0。

需要注意的是 alarm 闹钟并不能循环触发，只能触发一次。

pause()

pause() 用于使当前进程挂起（暂停执行），直到接收到一个信号为止。

当调用 pause() 时，当前进程会进入休眠状态，不再占用 CPU 资源。进程会一直保持休眠状态，直到接收到一个信号，并且该信号的处理函数已经执行完毕。一旦信号处理完成，pause() 返回，进程继续执行后续代码。

pause() 只会在接收到信号并且信号处理函数返回后才会返回，并且返回值总是 -1，并设置 errno 为 EINTR（表示系统调用被信号中断）。

setitimer()

setitimer () 允许程序在指定的时间间隔内生成信号。setitimer() 提供了比 alarm() 更精确的定时控制，适合需要周期性定时或高精度定时的场景。

    • ITIMER_REAL：真实时间（墙上时钟时间），到期时发送 SIGALRM 信号；
    • ITIMER_VIRTUAL：进程用户态 CPU 时间，到期时发送 SIGVTALRM 信号；
    • ITIMER_PROF：进程用户态+内核态 CPU 时间，到期时发送 SIGPROF 信号。

阻塞/未决信号集

在 PCB 中有两个非常重要的信号集。一个称之为“阻塞信号集”，另一个称之为“未决信号集”。

定义 当前被进程/线程阻塞的信号集合 被阻塞且已产生但尚未处理的信号集合

阻塞信号集仅需快速判断某个信号是否被阻塞，不需要记录信号的附加信息，所以使用一个一个 sigset_t 位掩码（通常为 unsigned long 数组）即可满足需求，每个 bit 对应一个信号。

而未决信号集中，同种标准信号多次到达时会被合并为一个，而实时信号则需要按顺序保存多个示例，所以需要链表结构。链表结构是为未决信号集的排队功能和数据完整性服务的。

信号屏蔽 sigprocmask()

内核为每一个进程维护了一个信号集，即信号掩码。当进程接收到一个属于信号掩码中定义的信号时，该信号就会被内核阻塞，无法传递给进程进行处理，直到该信号从信号掩码中移除。

向信号掩码中添加一个信号，通常有如下几种方式：

  1. 当通过 signal()、sigaction() 为信号设置处理函数时，系统自动将该信号加入进程的信号掩码，保证在处理一个信号时，不会重复触发同一信号（防止重入）。当信号处理函数结束后，系统会自动移除该信号。但是，如果使用 sigaction() 并设置 SA_NODEFER 标志，则不会自动阻塞该信号。
  2. 使用 sigaction() 函数为信号设置处理方式时，可以通过 sa_mask 参数额外指定一组需要阻塞的信号，这些信号会在处理函数执行期间被阻塞，处理结束后自动恢复。
  3. 使用 sigprocmask() 系统调用显式地向信号掩码中添加/移除信号。

发送实时信号 sigqueue()

Linux 内核定义了 31 个不同的实时信号，信号编号范围为 34~64，使用 SIGRTMIN 表示编号最小的实时信号，使用 SIGRTMAX 表示编号最大的实时信号。

和标准信号不同，内核对于实时信号所采取的是队列化管理，即如果将某一实时信号多次发送给另一个进程，那么将会多次传递此信号。当发送一个实时信号时，可为信号指定伴随数据（一整形数据或者指针值），供接收信号的进程在它的信号处理函数中获取。

sigqueue() 是 POSIX 标准中用于向指定进程发送信号并附带额外数据的函数，它比传统的 kill() 函数功能更强大，更适合发送实时信号。其函数原型为：

  • pid: 目标进程的进程 ID
  • sig: 要发送的信号编号（建议使用实时信号，即 SIGRTMIN 到 SIGRTMAX）
  • value: 附带的数据，是一个联合体，可以传递整数或指针
  • 返回值：成功时返回 0，失败时返回 -1 并设置 errno。

信号量

信号量是计算机科学中用于控制多线程/多进程对共享资源访问的同步机制，由荷兰计算机科学家 Dijkstra 在 1965 年提出。

信号量是一个整型变量，具有两个原子操作：

  1. P 操作：
    • 将信号量减 1
    • 如果信号量值变为负值，则进程/线程被阻塞
  2. V 操作：
    • 将信号量加 1
    • 如果有进程/线程因该信号量被阻塞，则唤醒其中一个

信号量有两种类型：

  1. 二进制信号量：值只能是 0 或者 1，用于互斥访问（类似于锁）
  2. 计数信号量：值可以是任意非负整数，用于控制对共享资源的访问

信号量主要是用来解决互斥/同步问题，比如经典的生产者——消费者问题，或者读者——写者问题。

信号量也可以用于进程间通信(IPC)，但它的主要作用不是直接传输数据，而是作为一种同步机制来协调多个进程对共享资源的访问。
