我们继续查看 portable 文件夹，我们使用 Keil MDK（即 Keil µVision） 开发环境，这里只介绍相关的移植文件：

名称 描述
Keil/ 指向 RVDS 文件夹
RVDS/ 不同内核芯片的移植文件
MemMang/ 内存管理相关文件

Keil/ 是一个重定向文件夹 ，只有一个 See-also-the-RVDS-directory.txt，意思是让我们看 RVDS/。

RVDS/ 包含 cortex-m0、m3、m4 和 m7 等内核的单片机的接口文件，主要由 port.c 和相关头文件两个文件构成，这个 port.c 就是 FreeRTOS 官方的技术人员写的接口文件。

MemMang/ 中有 5 个 C 文件，代表不同的内存管理策略实现，我们使用时只需要选择一个即可：

  • heap_1.c：最简单，只分配，不释放（适合无 vTaskDelete 的场景）
  • heap_2.c：支持释放，但不合并碎片（适合固定任务数）
  • heap_3.c：包装标准 malloc() 和 free()（需链接库支持）
  • heap_4.c：最佳匹配 + 合并相邻空闲块（最常用推荐 ）
  • heap_5.c：支持多段非连续内存堆（适用于复杂内存布局）

FreeRTOS 移植时需要的文件

在一个典型的 FreeRTOS 嵌入式项目中，你需要将以下文件加入编译：

  1. 构成基础功能的必须 C 文件：
    • tasks.c 任务调度核心
    • queue.c 队列实现
    • list.c 双向链表
    • 按需增加其余相关模块
  2. portable/ 中对应开发平台的接口文件 ：port.c 和头文件
  3. MemMang 中选择一个 heap_x.c 文件，一般选 heap_4.c
  4. 把所有 include/ 中的 .h 头文件路径加入编译器包含路径
  5. 一个 FreeRTOS 的核心配置文件 FreeRTOSConfig.h。

修改 HAL 时钟源

在使用 FreeRTOS 时，强烈建议 HAL 库不要使用 SysTick 作为时钟源，改用其他定时器（如 TIMx）来驱动 HAL 的时间基准。

这是因为 SysTick 中断通常被 FreeRTOS 用作系统时钟（tick），其优先级较低。假设在高于 SysTick 优先级的中断服务例程（ISR）中调用 HAL_Delay()，HAL_Delay() 在内部等待 SysTick_Handler 去递减延迟计数，但由于当前中断优先级高于 SysTick，所以 SysTick_Handler 永远不会执行。这会导致忙等待（busy-waiting），阻塞所有低于该中断优先级的中断，包括 FreeRTOS 的调度器中断。

这里演示在 CubeMAX 中，在 SYS 选择 HAL 时钟源的时候换成其他的，并且中断优先级设为 1，数值小表示高优先级，能及时更新时间。

任务的挂起与恢复

任务挂起（Suspend）与恢复（Resume） 是用于控制任务执行状态的重要机制。

通过挂起任务，可以使其进入挂起态，不再参与调度。通过恢复任务，就可以使其重新参与调度，恢复执行。

任务挂起

  • xTaskToSuspend：要挂起的任务句柄。如果传入 NULL，则挂起当前正在运行的任务。

需要将宏 INCLUDE_vTaskSuspend 配置为 1。

任务恢复

  • xTaskToResume：要恢复的任务句柄。

不论任务被使用 vTaskSuspend() 挂起多少次，只需调用 vTaskResume() 一次，即可使其继续执行，被恢复的任务会重新进入就绪状态。

需要将宏 INCLUDE_vTaskSuspend 配置为 1。

从中断服务程序中恢复任务

返回值：

  • pdTRUE：表示被恢复的任务具有比当前正在运行的任务更高的优先级，需要进行上下文切换（需调用 portYIELD_FROM_ISR()）。
  • pdFALSE：无需任务切换。

在中断服务程序中，不能调用可能引起阻塞的函数（如 vTaskResume()），且中断执行上下文不是任务上下文，不能直接进行任务切换。但你可能希望在中断处理完成后，立即运行某个高优先级任务。xTaskResumeFromISR 用于在中断服务程序（ISR）中安全地恢复任务，它会：

  1. 将目标任务从“挂起”态移出，变为就绪状态。
  2. 判断该任务的优先级是否高于当前正在运行的任务。
  3. 返回是否需要进行上下文切换。

需要将宏 INCLUDE_vTaskSuspend 和 INCLUDE_xTaskResumeFromISR 配置为 1。

[!NOTE]
在中断服务程序中调用 FreeRTOS 的 API 函数（特别是 xxxFromISR() 系列）时，中断的优先级不能高于 FreeRTOS 所管理的最高中断优先级。

原因：FreeRTOS 只能安全地管理优先级低于或等于某个阈值的中断，这个阈值由 configMAX_SYSCALL_INTERRUPT_PRIORITY 宏定义（也常称为“系统调用中断优先级”或“临界中断优先级”）。更详细的内容看下一章中断。

调度器的挂起与恢复

vTaskSuspendAll() 可以暂停 FreeRTOS 调度器的运行，禁止任何任务切换。

调度器被“挂起”，即使时间片到期或高优先级任务就绪，也不会发生任务切换。

注意，调度器挂起只是暂停了任务切换，但是并没有关闭中断，不会影响中断服务程序 ISR 的运行。

返回值：
- pdTRUE：有更高优先级任务已就绪，需要进行上下文切换（建议调用 taskYIELD()）。
- pdFALSE：无需切换。

恢复调度器后，检查是否有任务在挂起期间变为就绪状态，决定是否需要调度。

注意，xTaskResumeAll() 必须与 vTaskSuspendAll() 成对使用。

查看任务状态

  • pcWriteBuffer：指向一个字符数组（缓冲区）的指针，用于存储生成的任务列表字符串。

vTaskList() 是 FreeRTOS 提供的一个调试辅助函数，用于生成当前系统中所有任务的运行状态列表，它在开发和调试阶段非常有用，可以帮助开发者实时查看任务的优先级、堆栈使用情况、运行状态等信息。

缓冲区必须足够大，以容纳所有任务的信息（通常建议至少 256 字节，具体取决于任务数量）。

中断管理

在嵌入式系统中，中断是硬件或软件发出的信号，用于通知处理器某个事件需要立即处理。

中断发生时，处理器会暂停当前任务，跳转到对应的中断服务程序（ISR）执行，处理完成后返回原任务继续执行。

在使用 FreeRTOS 时，中断处理需要与任务调度协调：

  • 中断（ISR）：处理硬件事件（如定时器、串口接收），运行在中断上下文。
  • 任务（Task）：执行应用程序逻辑，运行在任务上下文。

典型模式是：中断 → 触发事件 → 通知任务 → 任务处理数据。

特点：

  1. 中断优先级高于任务：ISR 的执行优先级高于任何任务，确保及时响应外部事件。但 ISR 应尽可能短小，避免长时间阻塞任务调度。
  2. 禁止在 ISR 中直接调用普通的 FreeRTOS API：必须使用以 FromISR 结尾的特殊 API 函数。
  3. 中断与任务通信：ISR 通常不直接处理复杂逻辑，而是通过 API 通知任务。比如：
    1. 向队列发送数据（xQueueSendFromISR）
    2. 释放信号量（xSemaphoreGiveFromISR）
    3. 触发事件组（xEventGroupSetBitsFromISR）
    4. 唤醒特定任务（通过任务通知 xTaskNotifyFromISR）

FreeRTOS 的中断管理

STM32 基于 ARM Cortex-M 内核，使用嵌套向量中断控制器 NVIC（Nested Vectored Interrupt Controller） 管理中断。

STM32 中有 2 个优先级的概念：抢占优先级和响应优先级，每个中断都需要指定这两种优先级。其属性编号越小，表明它的优先级别越高（FreeRTOS 任务调度的任务优先级相反，是数值越大越优先）。

中断优先级是通过中断优先级配置寄存器的高4位 [7:4] 来配置的，只可以配置 16 种优先级，即抢占优先级和响应优先级的数量由一个 4 位的数字来决定：

分组方式 抢占优先级 响应优先级 可用组合
分组 0 0 位，取值为 0 4 位，取值为 0~15 无抢占嵌套，16 级响应
分组 1 1 位，取值为 0~1 3 位，取值为 0~7 2 组抢占，8 级响应
分组 2 2 位，取值为 0~3 2 位，取值为 0~3 4 组抢占，4 级响应（推荐）
分组 3 3 位，取值为 0~7 1 位，取值为 0~1 8 组抢占，2 级响应
分组 4 4 位，取值为 0~15 0 位，取值为 0 16 组抢占，无响应区分（实时性高）

[!NOTE]
实际开发中，为配合 FreeRTOS 使用，通常设置为 全抢占优先级（如 Group 4），避免抢占优先级带来的复杂性。

FreeRTOS 是一个实时操作系统，它本身不接管所有中断，而是 与 STM32 原生中断机制共存，它提供了自己的中断管理机制，主要是为了提供更强大和灵活的任务调度和管理功能。

前面提到，FreeRTOS 使用 SysTick 和 PendSV 这两个异常来实现任务调度，需要将它们的中断优先级设置为最低（即 15），为了让其他中断都能抢占任务调度过程，保证高优先级中断及时响应，满足实时性要求。

FreeRTOS 通过 BASEPRI 寄存器来管理中断，BASEPRI 是 Cortex-M 的一个特殊寄存器，用于设定处理器屏蔽中断的阈值。

当 BASEPRI > 0 时，所有优先级数值 大于等于 BASEPRI（低优先级） 的中断将被屏蔽，由 FreeRTOS 统一管理，而优先级数值 小于 BASEPRI（高优先级）的中断仍可响应。比如： BASEPRI设置为 0x50（只看高四位，也就是 5），代表中断优先级在 5~15 内的均被屏蔽，由 FreeRTOS 管理，0~4 的中断优先级正常执行。

FreeRTOS 的临界段代码

临界段代码（Critical Section），又称临界区，是指一段必须完整、连续执行、不能被中断打断的代码区域。

常见的应用场景：操作共享资源（全局变量、队列、信号量等）、数据结构的原子性操作、外设初始化等。

在 FreeRTOS 中，进入临界段代码时需要关闭中断，在处理完临界段代码后再重新开启中断。

FreeRTOS 提供了 4 个 API 来管理临界段：

函数宏 使用场景 说明
taskENTER_CRITICAL() 在任务中使用 进入(ENTER 临界段（关中断）
taskEXIT_CRITICAL() 在任务中使用 退出(EXIT)临界段（开中断）
taskENTER_CRITICAL_FROM_ISR() 在中断服务程序中使用 进入临界段（保存中断状态）
taskEXIT_CRITICAL_FROM_ISR() 在中断服务程序中使用 退出临界段（恢复中断状态）

进入和退出临界段是成对使用的，且支持嵌套调用。

每进入一次临界段，全局变量 uxCriticalNesting 都会加一，每调用一次退出临界段，uxCriticalNesting 减一，只有当 uxCriticalNesting 为 0 的时候才会调用函数 portENABLE_INTERRUPTS() 使能中断。

这确保了在存在多个临界段代码的情况下，不会因为某个临界段代码的退出而破坏其他临界段的保护。只有当所有的临界段代码都退出时，中断才会被重新使能。

FreeRTOS 时间管理

vTaskDelay() 和 xTaskDelayUntil() 是 FreeRTOS 中两个常用的任务延时函数，虽然都能实现“等待一段时间”的功能，但是二者有很大区别。

  • vTaskDelay()：相对延时。从当前时刻开始，延迟指定的节拍数后恢复运行。
  • xTaskDelayUntil()：绝对延时。将整个任务的运行周期视为一个整体，适用于需要以固定频率定期执行的任务。

FreeRTOS 消息队列

队列是任务间通信的主要形式。

它们可以用于在任务之间以及中断和任务之间发送消息。

在大多数情况下，队列用作线程安全的 FIFO（先进先出）缓冲区，新数据被发送到队列的后面，但也可以发送到前面。

队列是线程安全的数据结构，任务可以通过队列在彼此之间传递数据。有以下关键特点：

  1. FIFO顺序：队列采用先进先出 (FIFO) 的顺序，即先发送的消息会被先接收。
  2. 线程安全：队列操作是原子的，确保在多任务环境中的数据完整性。
  3. 阻塞和非阻塞操作：任务可以通过阻塞或非阻塞的方式发送和接收消息。如果队列满了或者为空，任务可以选择等待直到有空间或者数据可用，或者立即返回。
  4. 优先级继承：FreeRTOS 支持基于优先级的消息传递，确保高优先级任务在队列操作期间不会被低优先级任务阻塞。
  5. 可变长度项：队列中的项可以是不同长度的数据块，而不是固定大小。

使用队列，任务可以通过发送消息来共享信息，从而更好地协调和同步系统中的不同部分。
